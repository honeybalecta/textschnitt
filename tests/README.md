# Prüfläufe

Die Prüfläufe fahren die Desktop-Fassung von HoneyCut so, wie sie auch im Alltag läuft: das echte Backend (`textschnitt.py`), die echte Oberfläche in Chrome, echte Videos und echte Exporte über ffmpeg. Nachgestellt sind nur drei Dinge: Die Transkription liefert eine vorbereitete Wortliste, damit kein Whisper-Modell nötig ist; Dateidialoge lesen ihre Antwort aus einer Datei; und nichts verlässt den Rechner – die Abfrage bei GitHub und „im Browser öffnen“ landen in Dateien.

## Starten

```
cd tests && npm install        # einmalig: Playwright
tests/lauf.sh                  # alles (rund 10 Minuten, mit Vergleich rund 15)
tests/lauf.sh p_stand.mjs edit # eine einzelne Prüfung
HC_BASIS=v2.25.0 tests/lauf.sh # zusätzlich der Vergleich mit einer früheren Fassung
```

Gebraucht werden python3 mit numpy, ffmpeg, Node und Google Chrome (`HC_CHROME=/pfad/zu/chrome`, falls Chrome woanders liegt). Ist ein Java-Übersetzer da (`javac`), laufen auch die Tonklassen der Android-App mit; sonst wird dieser Teil ausgelassen. Alles, was die Läufe anlegen, liegt in `tests/.work/` (Testmedien, Datenordner, Protokolle, Bildschirmfotos, `out/bericht.md`); der Ordner lässt sich jederzeit löschen. Die Backends laufen auf den Ports 8795 und 8796 und kommen einer installierten HoneyCut-App nicht in die Quere.

## Was geprüft wird

| Datei | Inhalt |

| `backend_test.py` | Backend ohne Browser: sicheres Speichern, frühere Fassungen, Papierkorb, Speicher verwalten, alle Projekte sichern und einspielen (auch in einen anderen Datenordner), Projekt weitergeben mit eingebetteten Bildern (das Verhalten von Windows bei überlangen Pfaden ist nachgestellt), Vorschaubild der Projektliste, Textzeile und Untertitel im Export (Untertiteldatei, eingebrannt, Concat), Quellenzeilen und Textfassung, Schrift im Export (Maße der Schriftdateien, Größe und Umbruch wie in der Vorschau, eingebettete Schrift, Nachprüfung am Protokoll von ffmpeg, echte Probe-Exporte, Hinweis bei fehlender Schrift, Name der SRT-Datei), Hinweis aus dem eigenen Wörterbuch für Whisper (mit nachgestelltem Modell), Ton und Übergänge im Export (Verlauf für „Musik weicht der Sprache“ auch über die Stückelung langer Exporte hinweg, Rechenkern und Vorarbeit für „Stimme aufbereiten“, Übergänge bildgenau an `takt.mp4` abgelesen), Belege im Bild (unkenntlich gemachte Bereiche am Schachbrett ausgemessen: Rechteck, Ellipse mit Keyframes, Bildrand, Reihenfolge mit Formen und Fortschrittsbalken, Stückelung, CapCut und Concat; dazu die Probe, die auch der Selbsttest der Windows-App fährt), Hinweis auf neue Versionen, Fehlerbericht. Ein einzelner Teil: `python3 tests/backend_test.py ton_234` |
| `rechenkern.py` | Der Rechenkern von „Stimme aufbereiten“ in seinen drei Fassungen – Python (Windows-Export), JavaScript (Vorschau und Browser-Export, auch über dessen Weg in Stücken) und Java (Android-Export): dieselben Prüfsignale, Vergleich Abtastwert für Abtastwert. Dazu der Verlauf für „Musik weicht der Sprache“ und die übrigen Tonklassen der Android-App (`java/`, mit Nachbauten der Media3-Schnittstellen) |

| `p_schutz.mjs` | Rückgängig für Format, Ausschnitt und Lautstärke; Abgleich mehrerer Fenster; sichtbare Speicherfehler |
| `p_quellen.mjs` | Quellen und Belege: Quellen zu Aussagen (Zeile im Bild, Quellenliste), „Beleg nötig“ mit Hinweis vor dem Export, Bauchbinden (beim ersten Auftritt und von Hand), Prüfung auf Barrierefreiheit, Textfassung – auch in echten Exporten und in CapCut |

| `p_browser.mjs` | Browser-Export aus dem Plan (`web/engine.js`) in echtem Chrome, mit einer Attrappe an Stelle der Medienbibliothek (`attrappe/media.js`): Schnitte, Übergänge, Tempo, Bild-Einschub, „Musik weicht der Sprache“ und „Stimme aufbereiten“ – dieselben Erwartungen wie beim Windows-Export; dazu Belege im Bild: unkenntlich gemachte Bereiche am Schachbrett-Muster der Attrappe gemessen, Formen und Fortschrittsbalken als Bilder darüber |
| `p_stand.mjs` | Bearbeiten im Stand: Die Abspiellinie bleibt auf demselben Bild (zwölf Fälle je Projekt) |
| `p_wiedergabe.mjs` | Bearbeiten beim Abspielen: Die Wiedergabe läuft weiter (achtzehn Fälle je Projekt) |
| `v_plan.mjs` | Vergleich mit einer früheren Fassung: Exportplan, Untertitel, Zeitleiste und Umrechnungen aller Testprojekte |
| `v_bedienung.mjs` | Vergleich: dieselben Handgriffe mit Maus und Tastatur führen zum selben Projektstand |
| `v_export.mjs` | Vergleich: echte Exporte (Video, CapCut) liefern dasselbe Bild und denselben Ton |

Die Prüfungen mit `p_` müssen bestehen. Die Vergleiche mit `v_` melden Abweichungen als Hinweis: Ändert ein Update den Export oder die Bedienung mit Absicht, ist die Abweichung erwünscht und wird im Bericht sichtbar.

## Hilfsdateien

- `backend.py` startet das Test-Backend, `medien.py` erzeugt die Testmedien, `einrichten.mjs` legt die Testprojekte über die Oberfläche an (`kurz`, `lang`, `edit`, `editWord`, `stress`, `multi`), `drv.mjs` enthält die gemeinsamen Hilfen.
- `karo.mp4` aus `medien.py` ist ein Schachbrett aus 4 Pixel großen Feldern: Wo ein Export mittelt (verpixelt, weichzeichnet), wird es grau – so lässt sich die Lage eines Bereichs im fertigen Video auf den Pixel ausmessen.
- `takt.mp4` aus `medien.py` trägt in jedem Bild seine Nummer als Balkenmuster; `takt_lesen.py` liest sie aus einem fertigen Export wieder ab – bildgenau, bei Blenden mit dem Mischanteil. `ton_messen.py` misst den Pegel je Frequenzband über die Zeit. `rechenkern.mjs` rechnet die Prüffälle von `rechenkern.py` mit der JavaScript-Fassung.
- Auf GitHub startet `.github/workflows/test.yml` die Läufe bei jeder Änderung an `core/`, `textschnitt.py`, `tests/`, `web/engine.js` oder den Java-Tonklassen der Android-App und hängt den Bericht als Kommentar an den Commit.
